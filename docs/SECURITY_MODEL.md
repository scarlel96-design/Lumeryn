# Lumeryn 위협 모델 및 보안 설계 기준

> 상태: **설계 규격**. 실제 코드·샌드박스 보안 검증을 완료했다는 의미가 아니다.
> 적용 범위: 검색 코어, 전문 모듈, 사용자 정책, 모델·학습 데이터, 3중 개발 AI, Windows 앱.

## 1. 자산과 신뢰 경계

| 구역 | 데이터/프로세스 | 신뢰 수준 | 기본 동작 |
|---|---|---|---|
| 사용자 PC | 로컬 인증, 설정, 대화, 모델, 파일 | 보호 대상 | 최소 접근 |
| Lumeryn 도메인 | 의도·정책·근거·모듈 계약 | 내부 규칙 | 입력 검증 |
| 외부 웹·이미지·PDF | 검색 결과, HTML, 파일, OCR 텍스트 | 비신뢰 | 데이터로만 처리 |
| LLM 출력 | 응답, JSON, 도구 호출, 추론 결과 | 비신뢰 | 스키마·권한·근거 검사 |
| 선택형 플러그인 | 실행 코드, 모델 어댑터 | 최소 신뢰 | 권한·격리·승인 |
| 개발 AI 3종 | 외부 공급자와 각 CLI 도구 | 별도 신뢰 경계 | Worktree·비밀 분리 |
| 학습 데이터 | 외부 원문, 자동 생성 예제 | 출처에 따라 다름 | 검토 후 승격 |

## 3. 보안 결정의 우선순위

1. 외부 자료는 AI의 시스템 지침을 바꿀 수 없다.
2. LLM이 도구 실행을 제안하더라도 정책 게이트의 승인 없이는 실행하지 않는다.
3. 사용자 정의 응답 정책과 운영체제·네트워크 실행 권한은 별개다.
4. 사용자 승인 대상 작업은 대상·범위·효과를 명확히 설명한 후 실행한다.
5. 정책 판정이 실패하거나 권한 범위를 알 수 없으면 **쓰기 작업을 차단**한다.
6. 신뢰되지 않는 플러그인은 메인 Python 프로세스에 직접 적재하지 않는다.
7. 외부 AI 에이전트에게 비밀값·민감한 원문을 그대로 전달하지 않는다.
8. 보안 통제의 존재만으로 안전을 선언하지 않는다. 공격 시나리오 테스트가 필요하다.

## 4. 검색 수집기의 SSRF 요구사항

- 허용 프로토콜과 포트를 명시한다. 기본은 HTTP/HTTPS의 승인된 목적지만 허용한다.
- 요청 전 DNS 결과를 검사하고 연결 실제 IP·리다이렉트마다 재검사한다.
- 내부 주소·루프백·링크로컬·메타데이터 주소 및 사용자 정의 차단 대역을 네트워크 레벨에서 제한한다.
- 프록시, IPv6, URL 인코딩, IDN, DNS TTL 변경을 테스트한다.
- 크기·타임아웃·다운로드 속도·압축 해제 비율 상한을 적용한다.
- 브라우저 자동화 수집기는 격리 프로세스와 권한 제한을 적용한다.

문자열 기반 URL 검사만으로 SSRF 방어가 완료되었다고 판단하지 않는다.

## 5. 플러그인과 모듈 실행

모듈 매니페스트는 *메타데이터 계약*이다. 실제 OS 보안 경계가 아니다.
서명 및 패키지 출처 검증은 향후 플러그인 배포 단계에서 도입한다.
모듈 자동 로드, 원격 코드 다운로드, 임의 shell 명령 실행은 초기 기본값에서 금지한다.

## 6. 개발 에이전트 운영 보안

- 각 에이전트는 승인된 Worktree에서만 쓰기 작업을 수행한다.
- AI가 제공한 작업 완료 문장은 검증 증거가 아니다.
- 외부 Push, 릴리스, 결제, 시스템 설정 변경은 승인 확인 후 수행한다.
- 에이전트의 자식 프로세스, 시간제한, 종료 코드와 파일 변경을 점검한다.
- 환경 변수·인증 파일·비밀 토큰은 보고서와 실행 로그에서 제거한다.

## 7. 적용할 테스트와 출시 기준

P0: SEC-01/02/03/07/09/11의 중요 경로. P1: 나머지 전체.
고위험 권한 우회 또는 데이터 손상 결함이 있으면 출시는 NO-GO다.
검증 결과는 `PASS/FAIL/SKIP/NOT_RUN/BLOCKED`로 기록한다.
